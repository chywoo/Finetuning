# 첫 수업: 모델은 예제를 보며 무엇을 조금씩 바꿀까?

이 문서는 고등학교 수준의 수학과 짧은 Python 예제로 fine-tuning의 한 바퀴를 이해하는 수업이다. 먼저 **입력 → 다음 토큰의 확률 → 정답과 비교 → 가중치 수정 → 다시 확인**이라는 흐름을 잡는다.
큰 모델의 구조와 미분 공식을 전부 외우기 전에, 학습 명령의 숫자가 무엇을 뜻하는지 설명할 수 있으면 된다.
이 저장소의 실제 학습은 DGX Spark에서 진행한다. 아래 출력 숫자는 설명용 예시이며 Spark에서 측정한 결과가 아니다.

## 1. 이번에는 어디까지 공부할까?

첫 과제는 문장을 이어 쓰는 base LLM에 “사용자의 요청을 보고 답하라”는 패턴을 가르치는 것이다. 예를 들어 `Name two colors.`라는 요청에 `Red and blue.`라는 답을 주는 예제를 보여 준다.
이미 언어를 배운 모델을 출발점으로 삼아 조금 더 학습하는 일이 fine-tuning이다. 그중 모범 답이 있는 예제로 배우는 방식은 supervised fine-tuning, 줄여 SFT라고 부른다.
아무것도 배우지 않은 모델을 처음부터 만드는 사전학습보다 출발점이 훨씬 앞에 있다.

처음에는 다음 순서를 따라 한 단계씩 진행한다. 이 페이지에서는 첫 단계의 원리를 충분히 익힌다.

| 순서 | 할 일 | 그 단계에서 확인할 질문 |
|---|---|---|
| 1 | PyTorch로 LLM full fine-tuning | 학습 loop에서 실제로 무엇이 바뀌는가? |
| 2 | Hugging Face로 LoRA | 같은 목적을 적은 추가 가중치로 학습할 수 있는가? |
| 3 | Hugging Face로 도메인 적응 | 새 분야의 문서와 질문·답변은 어떻게 다른가? |
| 4 | DPO | 두 답 중 더 좋은 답을 고르는 예제를 어떻게 쓰는가? |
| 5 | Reward Model과 PPO | 답에 점수를 주는 모델과 그 점수로 배우는 모델은 어떻게 연결되는가? |
| 6 | GRPO | 여러 답의 상대적인 점수와 검증 가능한 정답을 어떻게 쓰는가? |
| 7 | VLM | 텍스트 질문에 이미지가 추가되면 입력과 평가가 어떻게 달라지는가? |

나머지 방법을 동시에 설치하거나 전부 비교할 필요는 없다.
[전체 학습 순서](11_curriculum.md)에서 다음 단계의 준비 조건을 확인하고, 첫 실습을 마친 뒤 하나씩 이동한다.

## 2. Python, 함수, 명령, 데이터 파일을 읽는 최소 기초

Python의 변수는 값에 붙이는 이름이다. `batch_size = 2`는 한 번에 읽을 예제 수를 2로 정했다는 뜻이다. `[1, 2, 3]`은 여러 값을 순서대로 담는 목록이고, `{"label": "healthy"}`는 이름과 값을 연결하는 사전이다.
함수는 반복할 작업에 이름을 붙인 것이다. 아래 함수는 두 값을 받아 더한 값을 돌려준다.

```python
def add(a, b):
    return a + b

result = add(2, 3)  # result는 5
```

나중에 `train_loop(model, train_loader, args, device)`를 읽을 때도 같은 방식으로 생각한다. `model`은 학습할 모델, `train_loader`는 예제를 조금씩 꺼내는 장치, 나머지는 설정과 계산 장치다.
함수 내부를 처음부터 모두 이해할 필요는 없다. 무엇을 받고 어떤 작업을 돌려주는지부터 표시한다.

터미널의 `python 01_instruction/pytorch/train.py --batch-size 2`는 Python에게 그 파일을 실행하라고 요청하는 명령이다. `--batch-size`는 설정 이름이고 뒤의 `2`가 설정값이다. 이런 명령 입력 방식을 CLI라고 한다.
`--dry-run`처럼 값이 없는 옵션은 기능을 켜는 스위치다. 이 실습에서는 데이터 확인만 하고 모델을 학습하지 않는다.
`python -m finetune_lab.prepare_data`의 `-m`은 파일 경로 대신 Python 모듈 이름으로 실행한다는 뜻이다.

JSON은 데이터를 글자로 저장하는 규칙이고, JSONL은 **한 줄에 예제 하나의 JSON 객체**를 저장하는 파일이다.

```jsonl
{"id":"toy-001","prompt":"Name two colors.","completion":"Red and blue."}
{"id":"toy-002","prompt":"What is 2 + 2?","completion":"4"}
```

`id`는 예제 이름, `prompt`는 모델에게 보여 줄 요청, `completion`은 학습시킬 답이다. 두 줄을 하나의 큰 목록으로 감싸지 않는다. 문자열은 큰따옴표로 감싸고 마지막 항목 뒤에 쉼표를 붙이지 않는다.
데이터 준비 코드는 원본 데이터를 이런 형태로 바꾸고, 학습 코드는 준비된 파일을 읽는다.
`data-dir`은 데이터를 읽을 폴더, `output-dir`은 학습한 모델과 기록을 저장할 폴더다.

## 3. 모델이 맞추는 것은 “다음 단어”보다 작은 토큰이다

`The sky is`를 보고 다음에 `blue`가 나올 가능성을 계산한다고 생각해 보자. LLM은 실제로는 단어, 단어의 일부, 문장부호 같은 조각인 **토큰**을 예측한다.
Tokenizer는 글을 이 조각들로 나누고 각 조각을 정수 번호인 token ID로 바꾸는 도구다.

| 사람이 읽는 조각 | 설명용 token ID |
|---|---|
| The | 11 |
| sky | 12 |
| is | 13 |
| blue | 21 |
| . | 22 |

표의 번호는 원리를 설명하기 위해 만든 값이며 실제 SmolLM2 tokenizer의 번호가 아니다. 실제 tokenizer에서는 공백이 조각에 포함되거나 `blue`가 다른 조각들로 나뉠 수도 있다.
한국어도 글자 또는 단어의 일부로 나뉠 수 있다. **단어 수와 토큰 수는 같지 않을 수 있다.**
Token ID가 21이라고 해서 11보다 두 배 중요하다는 뜻은 없다. 사전에서 조각을 찾기 위한 번호다.

모델 안에서는 각 번호를 계산용 숫자 묶음으로 바꾼 뒤 앞의 토큰들을 함께 처리한다. 그리고 다음 토큰 후보마다 점수를 계산하고, 전체 합이 1이 되는 확률로 바꾼다.
`max-length`는 대략 몇 개 토큰까지 입력에 넣을지 정하는 값이며 글자 수 제한과 다르다.
처음에는 “글을 번호로 바꿔 계산하고, 결과 번호를 다시 글로 바꾼다”는 연결만 이해하면 충분하다.

## 4. 정답을 얼마나 믿었는지로 loss를 계산한다

설명을 단순하게 하기 위해 `2 + 2 =` 뒤에는 `3`, `4`, `5` 세 후보만 있다고 가정하자. 실제 LLM의 후보는 훨씬 많지만 계산 원리는 같다. 이 예제의 정답은 `4`다.

| 다음 토큰 | 학습 전의 확률 | 조금 학습한 뒤의 확률 |
|---|---:|---:|
| 3 | 0.60 | 0.30 |
| 4: 정답 | 0.20 | 0.50 |
| 5 | 0.20 | 0.20 |
| 합계 | 1.00 | 1.00 |

학습 전에는 틀린 토큰 `3`에 가장 높은 확률을 줬다. 학습 후에는 정답 `4`를 더 믿도록 바뀌었다. 학습에서는 “맞았다/틀렸다”뿐 아니라 **정답 토큰에 얼마나 높은 확률을 줬는가**도 본다.
그 값을 작은 오류 점수인 loss로 바꾼다. 이 목표에서는 작을수록 정답 토큰을 더 잘 예측한 것이다.

다음 표는 정답 토큰 하나의 확률을 loss로 바꾼 값이다. 공식은 `loss = -ln(정답 확률)`이다.

| 정답에 준 확률 | loss: 자연로그 기준 | 읽는 방법 |
|---:|---:|---|
| 0.10 | 약 2.303 | 정답을 거의 믿지 않았다 |
| 0.20 | 약 1.609 | 정답에 낮은 확률을 줬다 |
| 0.50 | 약 0.693 | 정답에 절반의 확률을 줬다 |
| 0.80 | 약 0.223 | 정답에 높은 확률을 줬다 |

선택 보충: 계산기의 `ln`으로 `-ln(0.2)`와 `-ln(0.5)`를 계산해 보면 loss가 약 0.916 줄었다.
로그를 아직 배우지 않았다면 “정답 확률이 높을수록 loss가 작아진다”는 표의 관계부터 익힌다.
답이 여러 토큰이면 각 정답 토큰의 loss를 계산하고, 학습 대상 토큰들의 값을 평균한다. 같은 답을 모두 맞히는 두 모델도 정답에 준 확률이 다르면 loss가 다를 수 있다.
따라서 loss 0.7을 “정답률 70%”라고 읽으면 안 된다. Loss와 accuracy는 다른 지표다.

## 5. Gradient는 어느 숫자를 어느 방향으로 고칠지 알려 준다

모델에는 가중치라고 부르는 많은 숫자가 있다. 이 숫자들이 입력에 대한 예측 확률을 결정한다. 학습 코드는 정답의 loss를 계산한 뒤, 각 가중치가 loss를 키우는지 줄이는지 계산한다.
이 방향과 변화 정도를 나타내는 값이 gradient, 이를 거꾸로 계산하는 과정이 backpropagation이다.
Optimizer는 gradient를 받아 가중치를 조금 바꾼다. Learning rate는 기본적인 이동 크기를 조절한다.

장난감 예로 목표 숫자가 3이고 현재 조절 숫자 `w`가 1이라고 하자. 오류를 `(w - 3)²`으로 정하면 현재 오류는 4다. 이 점에서 기울기는 -4다.
학습률 0.1로 기울기의 반대 방향으로 움직이면 `w = 1 - 0.1 × (-4) = 1.4`가 된다.
새 오류는 `(1.4 - 3)² = 2.56`으로 줄었다. 미분을 모르면 우선 “3 쪽으로 조금 이동했다”로 읽어도 된다.

이 계산은 한 숫자짜리 연습이고 LLM의 실제 loss는 훨씬 복잡하다. LLM에서는 많은 가중치를 함께 바꾸며, 한 변화가 여러 입력의 예측에 영향을 준다.
그래서 한 문제의 답을 외우는 방향으로만 크게 바꾸면 다른 질문에 대한 능력이 떨어질 수 있다.
학습률을 크게 하거나 오래 학습한다고 언제나 더 좋아지는 것은 아니다.
PyTorch 첫 실습의 핵심은 `forward → loss → backward → optimizer.step()`을 직접 읽어 보는 것이다.

## 6. Batch, step, epoch를 8개 예제로 계산해 보자

예제 A부터 H까지 총 8개가 있고, 한 GPU에서 `batch-size=2`, `gradient-accumulation=2`라고 하자. Batch는 한 번에 함께 계산하는 예제 묶음이다. 여기서는 A와 B를 함께 읽는 묶음이 batch 하나다.
Gradient accumulation은 여러 batch의 gradient를 모은 뒤 가중치를 한 번 고치는 방법이다.

| 계산하는 작은 batch: microbatch | 예제 | 가중치 업데이트: optimizer step |
|---|---|---|
| 1 | A, B | gradient만 모은다 |
| 2 | C, D | 모은 gradient로 업데이트 1회 |
| 3 | E, F | gradient만 모은다 |
| 4 | G, H | 모은 gradient로 업데이트 1회 |

8개 예제를 한 번씩 모두 읽었으므로 **1 epoch = 4 microbatch = 2 optimizer step**이다.
Forward와 backward는 각각 4번, 가중치를 실제로 고치는 작업은 2번 수행했다.
한 번의 업데이트에 예제 4개가 참여하므로 유효 batch size는 `2 × 2 = 4`다.
3 epoch를 진행하면 예제 입력은 24회, microbatch는 12개, optimizer step은 6번이다.
이 표는 예제 길이와 평균 규칙을 단순화한 설명이다. 실제 코드에서는 답변 토큰 수에 맞춰 loss 평균을 맞춘다.

이 저장소의 `--max-steps`는 microbatch 수가 아니라 **optimizer 업데이트 수**다.
위의 8개 데이터에서 `--max-steps 2`라면 1 epoch에 해당하지만, 데이터가 24개라면 1/3 epoch다.
데이터 수가 바뀌면 같은 step 수가 같은 epoch 수를 뜻하지 않는다.
마지막 batch가 작거나 누적 묶음이 덜 찬 경우의 처리는 코드에서 확인하며, 처음에는 위처럼 나누어떨어지는 예제로 이해한다.

## 7. Train, validation, test는 서로 다른 일을 한다

Train은 모델이 정답을 보고 가중치를 고치는 연습 문제다. Validation은 중간에 모델이 좋아지고 있는지 확인하고 학습률이나 학습 길이를 고르는 문제다.
Test는 설정을 고른 뒤 마지막에 성능을 판단하는 문제다.

| 분할 | 정답으로 가중치를 고치는가? | 처음 실습에서 사용하는 목적 |
|---|---|---|
| train | 그렇다 | loss와 gradient로 학습 |
| validation | 아니다 | 학습 전후 확인, 설정 선택 |
| test | 아니다 | 선택을 끝낸 뒤 최종 비교 |

같은 문제가 이름만 바뀌어 train과 test에 들어가면 모델이 외운 답을 다시 시험하는 셈이다.
동일한 문서의 거의 같은 질문이나 같은 이미지를 다른 파일명으로 복사한 경우도 주의해야 한다.
이 저장소는 분할의 중복을 검사한다. 모든 의미상 중복까지 자동으로 찾는다는 뜻은 아니다.
Test 점수를 보고 매번 학습률을 바꾸면 test를 설정 선택에도 사용한 것이므로 마지막 시험의 의미가 약해진다.
첫 학습에서는 validation을 보고 설정을 결정하고, 마지막에 test를 확인하는 습관부터 익힌다.

## 8. Prompt는 보여 주되, 정답 점수는 completion에 준다

Instruction 학습에서는 입력 요청인 prompt와 모범 답인 completion을 합쳐 모델에 보여 준다. 학습 중에는 정답의 앞 토큰을 보고 다음 정답 토큰을 예측한다. 이를 teacher forcing이라고 한다.
각 토큰을 예측할 때 그 앞의 토큰까지만 보도록 계산을 제한하므로, 아직 예측할 정답 토큰을 미리 읽어 맞히는 것은 아니다.
실제로 답을 생성할 때는 데이터의 정답 대신 모델이 방금 생성한 토큰을 다음 입력으로 사용한다.

```text
### Instruction:
Name two colors.

### Response:
Red and blue.<EOS>
```

여기의 `<EOS>`는 설명용 표시다. 이 저장소에서는 JSONL의 답에 직접 적는 대신 encoder가 tokenizer의 실제 EOS ID를 붙인다.
Prompt는 답을 예측하는 데 필요한 조건이다. 여기서는 prompt 자체를 따라 쓰는 점수는 계산하지 않는다.
`labels=-100`은 “이 위치는 loss 계산에서 제외하라”는 표시다. -100이라는 단어를 모델에게 가르치는 것이 아니다.
Prompt를 input에서 지우는 것도 아니다. 모델은 여전히 그 입력을 보고 completion을 예측한다.

| 위치 | 질문 1 | 질문 2 | 답 1 | 답 2 | 실제 종료 | 길이 맞춤 | 길이 맞춤 |
|---|---:|---:|---:|---:|---:|---:|---:|
| 설명용 input ID | 11 | 12 | 21 | 22 | 2 | 2 | 2 |
| attention mask | 1 | 1 | 1 | 1 | 1 | 0 | 0 |
| loss용 labels | -100 | -100 | 21 | 22 | 2 | -100 | -100 |

EOS는 “이 답은 끝났다”는 신호이고, padding은 여러 예제의 길이를 맞추기 위한 빈 자리다. 이 표에서는 EOS와 padding의 ID를 같은 2로 썼지만 목적이 다르다. 실제 EOS는 학습하고 padding은 제외한다.
모든 ID 2를 지워 버리면 답을 끝내는 학습도 사라진다. 그래서 **ID뿐 아니라 실제 padding 위치**를 확인한다.
Attention mask는 입력 계산에서 padding을 구분하고, labels의 -100은 정답 loss 계산에서 제외할 위치를 구분한다.
둘의 역할은 다르다. Prompt는 attention에 참여하면서 정답 점수에서는 제외될 수 있다.
이 저장소의 causal LM은 모델 내부에서 다음 토큰에 맞게 입력과 정답을 한 칸 연결하므로 labels를 직접 다시 이동시키지 않는다.

## 9. Pretrained base, Instruct, post-training을 구분하자

사전학습은 많은 글을 읽으며 다음 토큰을 예측하는 능력을 만드는 과정이다. 그 결과인 pretrained base 모델은 문장과 지식을 어느 정도 다루지만 모든 입력을 사용자 요청으로 처리하도록 충분히 훈련되었다고 가정할 수 없다.
Base 모델도 간단한 지시를 따를 수 있다. “한 번도 지시를 따를 수 없는 모델”이라는 뜻은 아니다.
Instruct 모델은 지시·응답 예제 등의 추가 학습으로 요청에 맞게 답하는 능력을 조정한 모델이다.

Post-training은 사전학습 이후의 학습을 묶어 부르는 말이다. SFT로 모범 답을 학습하거나, DPO로 더 좋은 답을 선호하도록 조정하거나, 보상 기반 학습을 하는 과정이 여기에 들어갈 수 있다.
모든 Instruct 모델이 반드시 같은 SFT·DPO·PPO 순서로 만들어졌다는 뜻은 아니다.
첫 실습은 **SmolLM2-135M base → instruction SFT**이므로 같은 모델의 Instruct 버전으로 바꾸지 않고 시작한다.
135M은 약 1억 3,500만 개의 파라미터라는 뜻이다. 이미 언어를 배운 작은 모델로 학습 흐름을 관찰한다.

## 10. Full fine-tuning, LoRA, QLoRA와 저장 파일

Full fine-tuning은 원래 모델의 모든 가중치를 학습 대상으로 삼는 방식이다. 이미 만들어진 계산기의 내부 조절값 전체를 조정한다고 생각하면 가깝다.
첫 LLM PyTorch 실습은 이 방식으로 시작해 원래 가중치에 gradient가 생기고 optimizer가 바꾸는 흐름을 본다.

LoRA는 원래 가중치를 고정하고 작은 추가 조절 행렬, adapter를 붙여 그 부분을 학습한다.
원래 책을 보관하면서 수정 사항을 작은 별도 메모로 보관하는 비유를 쓸 수 있지만, 실제 메모는 텍스트 지시문이 아니라 숫자 행렬이다.
학습 가능한 숫자와 저장 파일이 줄어드는 장점이 있다. 원래 모델과 입력 계산에 필요한 메모리는 여전히 필요하다.
QLoRA는 고정된 원래 모델을 낮은 비트의 표현으로 읽으면서 LoRA adapter를 학습하는 접근이다.
4-bit 표현을 사용한다고 원래 모델의 모든 4-bit 값을 일반 full 학습처럼 직접 고치는 것은 아니다.

Checkpoint는 어느 시점의 모델 상태를 저장한 결과를 뜻한다. 다시 읽어 추론하거나 다음 작업의 출발점으로 쓸 수 있다. Full 모델 저장에는 모델 가중치와 설정, tokenizer가 필요하다. Adapter 저장에는 추가 가중치와 adapter 설정이 들어간다.
Adapter만으로는 원래 모델 전체가 없으므로 **같은 base 모델의 같은 revision + adapter + tokenizer**를 함께 읽는다.
정확히 중단 지점부터 학습을 이어가려면 optimizer·진행 상태 등도 필요하다. 모델 파일 저장만으로 완전한 resume가 보장되지는 않는다.
이 저장소의 metadata와 데이터 manifest는 어느 설정과 데이터로 만들었는지 추적하는 기록이다.

## 11. DGX Spark에서 명령을 읽는 방법

호스트는 DGX Spark의 원래 Linux 환경이고, 컨테이너는 그 안에서 실행하는 별도 소프트웨어 환경이다. GPU는 CUDA를 통해 계산에 사용한다. 이 저장소는 Spark의 ARM64와 GPU에 맞는 NVIDIA 컨테이너를 사용한다.
컨테이너를 실행할 때 저장소 폴더를 연결하므로 컨테이너 안의 `/workspace/finetune`에서 같은 코드와 데이터를 읽는다.
자세한 설치는 [DGX Spark 안내](04_dgx_spark.md)를 따른다. 실제 학습 명령은 Spark에서 실행한다.

```bash
# Spark 호스트의 저장소 폴더에서 컨테이너 시작
bash scripts/spark_container.sh hf
# 열린 컨테이너 안에서 설치하고 Python 환경 활성화
bash scripts/install_spark.sh hf
source .venv-spark-hf/bin/activate
```

컨테이너와 가상환경은 다르다. 컨테이너는 CUDA 등 시스템 환경을 제공하고, 활성화한 가상환경은 Python 패키지 선택을 맞춘다.
활성화 후의 `python` 명령이 실습용 환경을 사용하도록 한다. 이 첫 수업에서는 HF/PyTorch profile 하나로 진행한다.

## 12. 첫 실행에서 무엇을 기대해야 할까?

[빠른 시작](00_quickstart.md)을 따라 demo 데이터를 준비한 뒤, 아래 명령을 컨테이너에서 실행한다.
이미 `data/demo/instruction`이 준비되어 있다면 첫 데이터 준비 명령은 건너뛰고 기존 파일을 사용한다.

```bash
python -m finetune_lab.prepare_data --task instruction --source demo --output-root data/demo
python 01_instruction/pytorch/train.py --data-dir data/demo/instruction --dry-run
python 01_instruction/pytorch/train.py --data-dir data/demo/instruction \
  --smoke-model --device cuda --dtype auto --batch-size 2 \
  --gradient-accumulation 2 --max-steps 2 --max-length 64 \
  --output-dir outputs/foundations-smoke
```

이미 데이터나 모델이 저장된 폴더가 있으면 기존 결과를 덮어쓰기보다 새 출력 폴더 이름을 선택한다.
Dry run에서는 `train_examples`, `validation_examples`, `test_examples`, `dry_run: true` 같은 정보가 출력된다.
Demo instruction 데이터는 24/8/8개 예제로 구성된다. GPU를 학습시키지 않고 파일과 분할을 확인하는 단계다.
학습 중에는 다음과 같은 형태의 로그를 읽게 된다. **숫자는 형식을 보여 주는 가상 예시다.**

```jsonl
{"step":1,"train_loss":4.8}
{"step":2,"train_loss":4.6}
```

여기서 step 2는 optimizer가 두 번 업데이트됐다는 뜻이다. 위 설정은 train 24개 중 약 8개 입력을 처리한다.
실제 loss는 모델·예제·seed에 따라 다르고, 짧은 실행에서 반드시 감소하지도 않는다.
`--smoke-model`은 랜덤 tiny 모델의 실행·저장 경로 점검이다. 사전학습 모델의 fine-tuning 품질을 보여 주는 실험이 아니다.
그다음 실제 base 모델과 실제 데이터를 사용해 학습 전 평가, 학습, 별도 재로딩, 학습 후 평가를 진행한다.
Train loss가 내려가도 validation 답이 나빠지거나, 정답률이 오르지 않거나, 기존 능력이 떨어질 수 있다.
“실행 성공”, “저장·재로딩 성공”, “유효한 답 생성”, “성능 개선”을 각각 확인하고 실제 생성 답을 직접 읽는다.

## 13. 대학 수준의 수식으로 넘어가는 연결

이제 [이론 문서](01_theory.md)의 `L(θ) = -평균 log pθ(정답 토큰 | 앞의 토큰)`을 읽어 보자.
`θ`는 학습할 가중치 전체, `pθ`는 그 가중치로 계산한 확률, 평균은 loss를 계산하는 정답 위치들의 평균이다.
이번 수업의 정답 확률 표를 여러 예제와 답변 토큰으로 확장한 식이라고 생각하면 된다.
`∇θL`은 여러 가중치의 기울기를 묶은 gradient이고, 단순한 업데이트는 `θ새 = θ현재 - 학습률 × ∇θL`이다.
AdamW 같은 실제 optimizer는 gradient 기록 등을 사용하므로 이 한 줄보다 더 많은 계산을 한다.

LoRA의 `W' = W + (α/r)BA`에서는 `W`가 고정된 원래 행렬이고 `A`, `B`가 학습하는 작은 추가 행렬이다.
작은 숫자 하나를 바꾸던 장난감 gradient에서, 많은 숫자가 들어 있는 행렬을 바꾸는 학습으로 확대된다.
어려운 기호가 나오면 이 페이지의 확률 표, 작은 업데이트, batch 계산 중 어느 부분을 확장한 것인지 먼저 연결한다.
다음 학습은 [커리큘럼](11_curriculum.md)의 첫 PyTorch full 실습에서 시작하고, 마친 뒤 HF LoRA로 이동한다.

## 14. 스스로 확인하기: 먼저 답한 뒤 아래 해설을 보자

1. Token ID가 크면 그 토큰이 더 중요한가?
2. 정답 확률 0.2와 0.8 중 어느 쪽 loss가 작은가? Loss 0.7은 정답률 70%인가?
3. 예제 8개, batch 2, accumulation 2에서 1 epoch는 optimizer step 몇 번인가?
4. Prompt의 labels가 -100이면 모델이 prompt를 보지 못하는가?
5. EOS와 padding의 ID가 같을 때 모두 loss에서 제외해도 되는가?
6. Train loss가 감소하면 test 점수도 반드시 오르는가?
7. LoRA adapter 파일만 다른 base 모델에 붙이면 같은 결과가 나오는가?
8. Dry run 성공과 랜덤 smoke 모델 성공은 실제 모델의 GPU 학습·성능 개선을 보장하는가?

- 정답 1: 아니다. ID는 tokenizer의 조각을 구분하는 번호다.
- 정답 2: 0.8의 loss가 더 작다. Loss는 정답 확률로 계산한 오류값이고 정답률의 백분율이 아니다.
- 정답 3: 4개 microbatch를 처리하고 gradient를 두 batch씩 모으므로 optimizer 업데이트는 2번이다.
- 정답 4: 아니다. 입력에는 남아 있으며 답을 예측하는 조건이다. 정답 loss 계산에서만 제외된다.
- 정답 5: 안 된다. 실제 EOS는 종료 학습에 사용하고 길이 맞춤용 padding 위치만 제외한다.
- 정답 6: 아니다. 외운 예제에서 좋아져도 새로운 문제에서 나빠질 수 있으므로 분리해서 평가한다.
- 정답 7: 아니다. 동일한 원래 모델과 revision, adapter, tokenizer를 함께 읽어야 재현할 수 있다.
- 정답 8: 아니다. 두 점검의 범위는 다르며 실제 base 모델의 Spark 학습과 전후 평가가 따로 필요하다.
