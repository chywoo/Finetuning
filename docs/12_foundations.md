# 첫 수업: 모델은 예제를 보면서 어떻게 배울까요?

모델이 예제를 보고 배운다는 건 무슨 뜻일까요? 고등학교 수준의 수학과 짧은 Python 예제로 함께 알아봅시다. 먼저 **입력 → 다음 토큰의 확률 → 정답과 비교 → 가중치 수정 → 다시 확인**이라는 흐름을 살펴볼 거예요.

큰 모델의 구조나 미분 공식을 모두 외울 필요는 없습니다. 학습 명령에 들어가는 숫자가 무엇을 뜻하는지부터 차근차근 익혀 보세요. 아래 숫자는 이해를 돕기 위한 예시이지, 실제 실행 결과는 아닙니다. 실습 환경은 자신의 장치에 맞게 준비하면 됩니다.

## 1. 이번에는 어디까지 공부하나요?

첫 실습에서는 문장을 이어 쓰는 base LLM에 사용자의 요청을 보고 답하는 법을 가르쳐 봅니다. 예를 들어 `Name two colors.`라는 요청에 `Red and blue.`라는 답을 주는 예제를 보여 줍니다.
이미 언어를 배운 모델을 출발점으로 삼아 조금 더 학습하는 일이 fine-tuning입니다. 그중 모범 답안을 보며 배우는 방식을 supervised fine-tuning, 줄여 SFT라고 부릅니다.
처음부터 모델을 만드는 것과 달리, 이미 배운 언어 능력을 활용해서 시작할 수 있어요.

처음에는 다음 순서를 따라 한 단계씩 진행해 보세요. 이 페이지에서는 첫 단계의 원리부터 충분히 익혀 봅시다.

|---|---|---|

## 2. Python과 명령어, 데이터 파일부터 읽어 볼까요?

Python의 변수는 값에 붙이는 이름입니다. `batch_size = 2`는 한 번에 읽을 예제 수를 2로 정했다는 뜻입니다. `[1, 2, 3]`은 여러 값을 순서대로 담는 목록이고, `{"label": "healthy"}`는 이름과 값을 연결하는 사전입니다.
함수는 반복할 작업에 이름을 붙인 것입니다. 아래 함수는 두 값을 받아 더한 값을 돌려줍니다.

```python
def add(a, b):
    return a + b

result = add(2, 3)  # result는 5
```

나중에 `train_loop(model, train_loader, args, device)`를 읽을 때도 같은 방식으로 생각해 보세요. `model`은 학습할 모델, `train_loader`는 예제를 조금씩 꺼내는 장치, 나머지는 설정과 계산 장치입니다.
함수 안의 코드를 처음부터 모두 이해할 필요는 없습니다. 어떤 값을 받아서 무슨 일을 하고, 무엇을 돌려주는지부터 살펴보세요.

터미널의 `python 01_instruction/pytorch/train.py --batch-size 2`는 Python에게 그 파일을 실행하라고 요청하는 명령입니다. `--batch-size`는 설정 이름이고 뒤의 `2`가 설정값입니다. 이런 명령 입력 방식을 CLI라고 합니다.
`--dry-run`처럼 값이 없는 옵션은 기능을 켜는 스위치입니다. 이 실습에서는 데이터 확인만 하고 모델을 학습하지 않습니다.
`python -m finetune_lab.prepare_data`의 `-m`은 파일 경로 대신 Python 모듈 이름으로 실행한다는 뜻입니다.

JSON은 데이터를 글자로 저장하는 규칙이고, JSONL은 **한 줄에 예제 하나의 JSON 객체**를 저장하는 파일입니다.

```jsonl
{"id":"toy-001","prompt":"Name two colors.","completion":"Red and blue."}
{"id":"toy-002","prompt":"What is 2 + 2?","completion":"4"}
```

`id`는 예제 이름, `prompt`는 모델에게 보여 줄 요청, `completion`은 학습시킬 답입니다. 두 줄을 하나의 큰 목록으로 감싸지 않습니다. 문자열은 큰따옴표로 감싸고 마지막 항목 뒤에 쉼표를 붙이지 않습니다.
데이터 준비 코드는 원본 데이터를 이런 형태로 바꾸고, 학습 코드는 준비된 파일을 읽습니다.
`data-dir`은 데이터를 읽을 폴더, `output-dir`은 학습한 모델과 기록을 저장할 폴더입니다.

## 3. 모델은 단어보다 작은 조각인 토큰을 예측해요

`The sky is`를 보고 다음에 `blue`가 나올 가능성을 계산한다고 생각해 보세요. LLM은 실제로는 단어, 단어의 일부, 문장부호 같은 조각인 **토큰**을 예측합니다.
Tokenizer는 글을 이 조각들로 나누고 각 조각을 정수 번호인 token ID로 바꾸는 도구입니다.

답변 끝에는 보통 **EOS**라는 특별한 토큰을 붙입니다. EOS는 “여기서 답변이 끝났어요”라는 표시예요. 모델이 EOS를 배우면 답을 어디서 마칠지도 알 수 있습니다. Section 8에서 EOS와 비슷해 보이는 padding이 어떻게 다른지 살펴볼게요.

| 사람이 읽는 조각 | 설명용 token ID |
|---|---|
| The | 11 |
| sky | 12 |
| is | 13 |
| blue | 21 |
| . | 22 |

표의 번호는 원리를 설명하기 위해 만든 값이며 실제 SmolLM2 tokenizer의 번호가 아닙니다. 실제 tokenizer에서는 공백이 조각에 포함되거나 `blue`가 다른 조각들로 나뉠 수도 있어요.
한국어도 글자 또는 단어의 일부로 나뉠 수 있어요. **단어 수와 토큰 수는 같지 않을 수 있어요.**
Token ID가 21이라고 해서 11보다 두 배 중요하다는 뜻은 아닙니다. 사전에서 조각을 찾기 위한 번호입니다.

모델 안에서는 각 번호를 계산용 숫자 묶음으로 바꾼 뒤 앞의 토큰들을 함께 처리합니다. 그리고 다음 토큰 후보마다 점수를 계산하고, 전체 합이 1이 되는 확률로 바꿉니다.
`max-length`는 대략 몇 개 토큰까지 입력에 넣을지 정하는 값이며 글자 수 제한과 다릅니다.
처음에는 “글을 번호로 바꿔 계산하고, 결과 번호를 다시 글로 바꾼다”는 연결만 이해하면 충분합니다.

## 4. 정답에 준 확률로 loss를 계산해 봅시다

설명을 단순하게 하기 위해 `2 + 2 =` 뒤에는 `3`, `4`, `5` 세 후보만 있다고 가정해 봅시다. 실제 LLM의 후보는 훨씬 많지만 계산 원리는 같습니다. 이 예제의 정답은 `4`입니다.

| 다음 토큰 | 학습 전의 확률 | 조금 학습한 뒤의 확률 |
|---|---:|---:|
| 3 | 0.60 | 0.30 |
| 4: 정답 | 0.20 | 0.50 |
| 5 | 0.20 | 0.20 |
| 합계 | 1.00 | 1.00 |

학습 전에는 틀린 토큰 `3`에 가장 높은 확률을 줬어요. 학습 후에는 정답 `4`를 더 믿도록 바뀌었어요. 학습에서는 “맞았다/틀렸다”뿐 아니라 **정답 토큰에 얼마나 높은 확률을 줬는가**도 봅니다.
정답에 준 확률을 오류를 나타내는 점수인 loss로 바꿉니다. 이 목표에서는 작을수록 정답 토큰을 더 잘 예측한 것입니다.

다음 표는 정답 토큰 하나의 확률을 loss로 바꾼 값입니다. 공식은 `loss = -ln(정답 확률)`입니다.

| 정답에 준 확률 | loss: 자연로그 기준 | 읽는 방법 |
|---:|---:|---|
| 0.10 | 약 2.303 | 정답을 거의 믿지 않았다 |
| 0.20 | 약 1.609 | 정답에 낮은 확률을 줬다 |
| 0.50 | 약 0.693 | 정답에 절반의 확률을 줬다 |
| 0.80 | 약 0.223 | 정답에 높은 확률을 줬다 |

조금 더 궁금하다면:  계산기의 `ln`으로 `-ln(0.2)`와 `-ln(0.5)`를 계산해 보면 두 loss의 차이가 약 0.916이라는 것을 확인할 수 있어요.
로그를 아직 배우지 않았다면 “정답 확률이 높을수록 loss가 작아진다”는 표의 관계부터 익혀 보세요.
답이 여러 토큰이면 각 정답 토큰의 loss를 계산하고, 학습 대상 토큰들의 값을 평균합니다. 같은 답을 모두 맞히는 두 모델도 정답에 준 확률이 다르면 loss가 다를 수 있어요.
여기서 헷갈리지 마세요. Loss 0.7은 “정답률 70%”라는 뜻이 아닙니다. Loss와 accuracy는 다른 지표입니다.

## 5. Gradient는 숫자를 어느 방향으로 바꿀지 알려 줘요

모델에는 가중치라고 부르는 많은 숫자가 있습니다. 이 숫자들이 입력에 대한 예측 확률을 결정합니다. 학습 코드는 정답의 loss를 계산한 뒤, 각 가중치가 loss를 키우는지 줄이는지 계산합니다.
Gradient는 가중치를 조금 바꿀 때 loss가 어느 방향으로 얼마나 변하는지 알려 주는 값입니다. 모델의 출력에서 입력 쪽으로 거슬러 올라가며 gradient를 계산하는 과정을 backpropagation, 즉 역전파라고 부릅니다.
Optimizer는 gradient를 받아 가중치를 조금 바꿉니다. Learning rate는 기본적인 이동 크기를 조절합니다.

간단한 예로 목표 숫자가 3이고 현재 조절 숫자 `w`가 1이라고 해 봅시다. 오류를 `(w - 3)²`으로 정하면 현재 오류는 4입니다. 이 점에서 기울기는 -4입니다.
학습률 0.1로 기울기의 반대 방향으로 움직이면 `w = 1 - 0.1 × (-4) = 1.4`가 됩니다.
새 오류는 `(1.4 - 3)² = 2.56`으로 줄었어요. 미분을 모르면 우선 “3 쪽으로 조금 이동했다”로 읽어도 괜찮습니다.

이 계산은 숫자 하나로 해 보는 연습이고 LLM의 실제 loss는 훨씬 복잡합니다. LLM에서는 많은 가중치를 함께 바꾸며, 한 변화가 여러 입력의 예측에 영향을 줍니다.
그래서 한 문제의 답을 외우는 방향으로만 크게 바꾸면 다른 질문에 대한 능력이 떨어질 수 있어요.
학습률을 크게 하거나 오래 학습한다고 언제나 더 좋아지는 것은 아닙니다.
첫 PyTorch 실습에서는 `forward → loss → backward → optimizer.step()`을 따라가며 각 단계가 무슨 일을 하는지 살펴보세요.

## 6. 몇 개씩 읽고, 언제 모델을 바꾸나요?

문제집에 문제가 8개 있다고 생각해 보세요. 모델도 예제를 몇 개씩 읽고, 그 결과를 바탕으로 가중치를 조금씩 바꿉니다. 이때 **읽는 횟수와 가중치를 바꾸는 횟수는 다를 수 있어요.**

먼저 세 가지 말을 구분해 봅시다.

- **Batch:** 한 번에 함께 읽는 예제 묶음입니다. `batch-size=2`이면 예제 2개를 함께 계산합니다.
- **Step:** 여기서는 가중치를 한 번 바꾸는 것을 뜻합니다. 정확히는 optimizer step이라고 부릅니다.
- **Epoch:** 준비한 학습 예제를 처음부터 끝까지 한 번씩 읽는 것입니다. 문제집 한 권을 한 바퀴 푸는 셈이지요.

### 예제 2개씩 읽고, 두 묶음마다 한 번 바꿔 볼까요?

예제 A부터 H까지 8개를 준비했다고 해 봅시다. 설정은 다음과 같습니다.

- `--batch-size 2`: 한 번에 예제 2개를 읽습니다.
- `--gradient-accumulation 2`: 두 묶음의 계산 결과를 모은 뒤 가중치를 한 번 바꿉니다.

여기서 모으는 계산 결과는 앞 절에서 배운 gradient입니다. “가중치를 어느 방향으로 바꾸면 좋을지”를 두 묶음에서 함께 알아보는 거예요.

| 읽는 순서 | 함께 읽는 예제 | 읽은 뒤에 하는 일 |
|---|---|---|
| 첫 번째 묶음 | A, B | 바꿀 방향만 계산해 모아 둡니다. |
| 두 번째 묶음 | C, D | 두 묶음의 결과로 가중치를 바꿉니다. **1 step** |
| 세 번째 묶음 | E, F | 다시 바꿀 방향만 계산해 모아 둡니다. |
| 네 번째 묶음 | G, H | 두 묶음의 결과로 가중치를 바꿉니다. **2 step** |

이제 예제 8개를 모두 읽었으니 **1 epoch**를 마쳤습니다. 읽기는 네 번 했지만, 가중치는 두 번만 바꿨어요.

정리하면 다음과 같습니다.

- 한 번에 읽은 예제: 2개
- 가중치를 한 번 바꾸는 데 사용한 예제: `2개 × 2묶음 = 4개`
- 예제 8개를 한 바퀴 읽는 데 필요한 업데이트: `8 ÷ 4 = 2 step`

가중치를 한 번 바꿀 때 사용하는 예제 수를 **유효 batch size**라고 합니다. 여러 묶음에 나눠 계산하면 한꺼번에 큰 묶음을 처리할 때보다 메모리 부담을 줄일 수 있습니다. 나눠 읽는 작은 묶음은 microbatch, 계산 결과를 모으는 방법은 gradient accumulation이라고 부릅니다.

### 명령의 숫자는 어떻게 읽으면 될까요?

이 실습 코드에서 `--max-steps 2`는 “가중치를 두 번 바꾼 뒤 멈춰라”라는 뜻입니다. 예제를 두 개 읽으라는 뜻은 아닙니다.

위 설정에서 학습 데이터가 8개라면 2 step은 한 바퀴입니다. 데이터가 24개라면 8개만 읽었으니 전체의 1/3바퀴예요. 그래서 **step 수가 같아도 데이터 수가 다르면 몇 바퀴 공부했는지는 달라집니다.**

예제 8개를 3 epoch 동안 학습한다면 같은 예제를 세 번씩 읽습니다. 총 24개 분량을 읽고, 가중치는 6번 바꿉니다.

처음에는 위처럼 딱 나누어떨어지는 경우부터 이해해 보세요. 마지막 묶음에 예제가 적게 남는 경우는 이후 학습 루프에서 살펴봅니다. 실제 텍스트 학습에서는 답변 길이도 다르므로, 각 묶음의 loss를 합칠 때 학습 대상 토큰 수도 고려합니다.

## 7. 연습 문제, 중간 점검, 마지막 시험을 나눠요

모델이 학습한 문제를 그대로 다시 풀게 하면 잘할 수 있습니다. 하지만 그것만으로 처음 보는 문제도 잘 푼다고 말할 수는 없겠지요.

그래서 데이터를 세 묶음으로 나눕니다. 이런 구분을 **데이터 분할**, 또는 split이라고 합니다.

| 이름 | 공부에 비유하면 | 어떻게 쓰나요? |
|---|---|---|
| **Train** | 정답을 보며 푸는 연습 문제 | 이 데이터로 loss를 계산하고 가중치를 바꿉니다. |
| **Validation** | 공부 방법을 고르는 중간 점검 | 결과를 보고 학습률이나 학습 횟수 같은 설정을 고릅니다. 가중치를 직접 바꾸는 학습에는 넣지 않습니다. |
| **Test** | 모든 준비를 끝낸 뒤 보는 마지막 시험 | 설정을 다 고른 뒤, 학습에 쓰지 않은 문제에서 성능을 확인합니다. |

예를 들어 예제가 100개라면 80개를 연습용, 10개를 중간 점검용, 나머지 10개를 마지막 시험용으로 나눌 수 있습니다. 이 숫자는 설명용 예시이고, 실제 실습의 분할 수는 데이터 안내를 따릅니다.

### 왜 validation과 test까지 따로 나눌까요?

학습률을 바꿔 가며 validation 결과를 여러 번 비교할 수 있습니다. 그러면 점점 validation에서 잘되는 설정을 고르게 됩니다.

이때 test까지 계속 확인하며 설정을 바꾸면 어떻게 될까요? 마지막 시험 문제를 미리 보면서 공부 방법을 고르는 셈입니다. 그래서 **설정은 validation으로 고르고, test는 최종 비교에 사용합니다.**

### 같은 문제가 다른 묶음에 들어가지 않게 해 주세요

학습 문제와 시험 문제가 같다면 외운 답을 다시 묻는 셈입니다. 파일 이름이나 예제 번호가 다르더라도 내용이 같으면 주의해야 합니다.

- 같은 질문과 답변을 이름만 바꿔 넣지 않았나요?
- 같은 문서에서 나온 거의 같은 질문이 나뉘어 들어가지 않았나요?
- 같은 이미지를 다른 파일명으로 복사하지 않았나요?

이 실습의 데이터 검사 코드는 정해진 기준에 따라 중복을 찾습니다. 하지만 뜻이 비슷한 문장이나 같은 출처의 자료까지 모두 알아서 찾아 주지는 않습니다. 직접 데이터 예시도 읽어 보세요.

## 8. 질문은 읽게 하고, 답변을 잘 쓰는지 평가해요

모델에게 다음 예제를 보여 준다고 해 봅시다.

```text
### Instruction:
Name two colors.

### Response:
Red and blue.<EOS>
```

질문인 `Name two colors.`를 **prompt**, 모범 답인 `Red and blue.`를 **completion**이라고 합니다. 질문과 답변을 함께 입력하지만, 이 Instruction SFT 실습에서는 **답변을 잘 예측했는지에 대해서만 loss를 계산합니다.**

질문을 따라 쓰는 연습이 아니라, 질문을 읽고 답하는 연습을 하고 싶기 때문입니다.

### 정답을 보여 주면 미리 답을 읽는 것 아닌가요?

학습할 때는 모범 답의 앞부분을 보여 주면서 다음 토큰을 예측하게 합니다. 단어 단위로 단순하게 생각하면 다음과 같아요.

- 질문을 읽고 답변의 첫 부분인 `Red`를 예측합니다.
- 질문과 정답의 `Red`를 보고 다음 부분인 `and`를 예측합니다.
- 질문과 정답의 `Red and`를 보고 다음 부분인 `blue`를 예측합니다.

각 위치에서는 **그 앞의 토큰만 볼 수 있습니다.** 아직 예측해야 할 토큰이나 그 뒤의 정답을 미리 볼 수는 없어요. 이렇게 정답의 앞부분을 이용해 배우는 방법을 teacher forcing이라고 합니다.

실제로 답변을 만들 때는 모범 답을 받지 않습니다. 모델이 방금 만든 토큰을 다음 입력으로 사용하며 답을 이어 갑니다. 학습 때와 달리 앞에서 틀린 내용을 만들면 뒤의 답변에도 영향을 줄 수 있습니다.

### `labels=-100`은 “여기는 채점하지 마세요”라는 표시예요

모델에 보여 주는 내용과 점수를 계산하는 대상은 서로 다른 정보입니다. 각각 별도의 표식으로 알려 준다고 생각하면 쉬워요.

- **Input Token ID:** 질문과 답변을 토큰으로 나누고 번호를 붙인 입력입니다. 모델이 실제로 읽는 내용이에요.
- **Attention mask:** 각 입력 위치에 실제 토큰이 있는지 표시합니다. `1`은 읽을 내용, `0`은 길이를 맞추려고 넣은 빈칸입니다.
- **Labels:** 답변 중 어느 위치를 채점할지 표시합니다. 답변 토큰은 정답 번호를 적고, 채점하지 않을 곳은 `-100`을 적습니다.

질문에는 `attention mask=1`을 주기 때문에 모델은 질문을 읽습니다. 동시에 질문의 `labels=-100`은 질문을 따라 썼는지 채점하지 말라는 뜻이에요. 따라서 **질문은 답을 만들 때 참고하지만, 정답 점수는 답변에 대해서만 계산합니다.**

`-100`은 모델에게 입력하는 단어나 Token ID가 아닙니다. 학습 코드가 loss를 계산할 때 “이 위치는 건너뛰라”고 알려 주는 표시입니다.

### 답의 끝과 빈칸도 구분해 봅시다

- **EOS:** “답변이 여기서 끝났어요”라는 표시입니다. 언제 답을 끝낼지도 배워야 하므로 loss 계산에 포함합니다.
- **Padding:** 서로 길이가 다른 예제를 한 묶음으로 계산하려고 덧붙인 빈칸입니다. 정답이 아니므로 loss 계산에서 제외합니다.

예를 들어 한 답변은 토큰 5개, 다른 답변은 7개라면 짧은 쪽에 빈칸 2개를 붙여 길이를 맞출 수 있습니다.

위 예제의 `<EOS>`는 설명용 표시입니다. 데이터 파일에 직접 적지 않아도 이 실습의 데이터 처리 코드가 tokenizer의 실제 EOS ID를 붙입니다.

### 코드의 표시는 이렇게 연결하면 됩니다

아래 표의 숫자는 설명용입니다. 질문과 답변을 각각 Token 2개로 줄여 표현했고, EOS와 padding은 같은 Token ID `2`를 쓴다고 가정했습니다. 같은 번호라도 답의 끝인지 빈칸인지는 위치와 mask를 보고 구분합니다.

| 위치 | 질문 1 | 질문 2 | 답 1 | 답 2 | 답의 끝 | 빈칸 | 빈칸 |
|---|---|---|---|---|---|---|---|
| Input Token ID | 11 | 12 | 21 | 22 | 2 (EOS) | 2 (빈칸) | 2 (빈칸) |
| Attention mask | 1 | 1 | 1 | 1 | 1 | 0 | 0 |
| Labels | -100 | -100 | 21 | 22 | 2 | -100 | -100 |

두 표시의 역할을 따로 생각해 보세요.

- **Input Token ID:** 모델이 읽는 토큰의 번호입니다. 숫자 자체에 중요도나 크기 순서의 뜻은 없습니다.
- **Attention mask:** 모델이 읽을 실제 입력과 채우기용 빈칸을 구별합니다. 실제 질문·답변·EOS는 `1`, 빈칸은 `0`입니다. 뒤쪽 토큰을 미리 못 보게 하는 규칙과는 다른 역할입니다.
- **Labels:** 정답 점수를 계산할 위치를 알려 줍니다. 질문은 `-100`, 답변과 EOS는 정답 Token ID, 빈칸은 `-100`입니다.

질문 위치를 보세요. Input Token ID에는 질문 번호가 있고 attention mask는 `1`이라 모델이 질문을 읽습니다. 하지만 labels는 `-100`이라 질문을 따라 썼는지 점수를 매기지 않아요. **읽기는 하지만 채점하지 않는 것**입니다.

EOS와 padding의 Token ID가 둘 다 `2`여도 역할은 다릅니다. EOS 위치는 attention mask가 `1`이고 Labels가 `2`이므로 답의 끝으로 학습합니다. 빈칸은 attention mask가 `0`이고 Labels가 `-100`이므로 계산에서 빠집니다. **번호만 보지 말고 위치와 두 표식을 함께 보세요.**

마지막으로, 이 프로젝트에서 쓰는 언어 모델은 입력의 앞부분으로 다음 토큰을 예측하도록 내부에서 위치를 맞춰 줍니다. 처음에는 labels의 정답 번호를 직접 한 칸 옮기지 않아도 된다는 점만 기억해 두세요.

## 9. Base, Instruct, post-training은 어떻게 다른가요?

사전학습은 많은 글을 읽으며 다음 토큰을 예측하는 능력을 만드는 과정입니다. 그 결과인 pretrained base 모델은 문장과 지식을 어느 정도 다루지만 모든 입력을 사용자 요청으로 처리하도록 충분히 훈련되었다고 가정할 수 없습니다.
Base 모델도 간단한 지시를 따를 수 있어요. “한 번도 지시를 따를 수 없는 모델”이라는 뜻은 아닙니다.
Instruct 모델은 지시·응답 예제 등의 추가 학습으로 요청에 맞게 답하는 능력을 조정한 모델입니다.

Post-training은 사전학습 이후의 학습을 묶어 부르는 말입니다. SFT로 모범 답을 학습하거나, DPO로 더 좋은 답을 선호하도록 조정하거나, 보상 기반 학습을 하는 과정이 여기에 들어갈 수 있어요.
모든 Instruct 모델이 반드시 같은 SFT·DPO·PPO 순서로 만들어졌다는 뜻은 아닙니다.
첫 실습은 **SmolLM2-135M base → instruction SFT**이므로 같은 모델의 Instruct 버전으로 바꾸지 않고 시작합니다.
135M은 약 1억 3,500만 개의 파라미터라는 뜻입니다. 이미 언어를 배운 작은 모델로 학습 흐름을 살펴봅니다.

## 10. Full fine-tuning, LoRA, QLoRA와 저장 파일

Full fine-tuning은 원래 모델의 모든 가중치를 학습 대상으로 삼는 방식입니다. 이미 만들어진 계산기의 내부 조절값 전체를 조정한다고 생각하면 비슷합니다.
첫 LLM PyTorch 실습은 이 방식으로 시작해 원래 가중치에 gradient가 생기고 optimizer가 바꾸는 흐름을 봅니다.

LoRA는 원래 가중치를 고정하고 작은 추가 조절 행렬, adapter를 붙여 그 부분을 학습합니다.
원래 책은 그대로 두고 수정할 내용을 작은 메모에 따로 적는다고 생각해 보세요. 다만 실제 adapter는 글로 쓴 지시문이 아니라 숫자 행렬입니다.
학습 가능한 숫자와 저장 파일이 줄어드는 장점이 있습니다. 원래 모델과 입력 계산에 필요한 메모리는 여전히 필요합니다.
QLoRA는 고정된 원래 모델을 낮은 비트의 표현으로 읽으면서 LoRA adapter를 학습하는 방법입니다.
4-bit 표현을 사용한다고 원래 모델의 모든 4-bit 값을 일반 full 학습처럼 직접 고치는 것은 아닙니다.

Checkpoint는 어느 시점의 모델 상태를 저장한 결과를 뜻합니다. 다시 읽어 추론하거나 다음 작업의 출발점으로 쓸 수 있어요. Full 모델 저장에는 모델 가중치와 설정, tokenizer가 필요합니다. Adapter 저장에는 추가 가중치와 adapter 설정이 들어갑니다.
Adapter만으로는 원래 모델 전체가 없으므로 **같은 base 모델의 같은 revision + adapter + tokenizer**를 함께 읽습니다.
정확히 중단 지점부터 학습을 이어가려면 optimizer·진행 상태 등도 필요합니다. 모델 파일 저장만으로 완전한 resume가 보장되지는 않습니다.
이 실습 코드가 저장하는 metadata와 데이터 manifest에는 사용한 설정과 데이터 정보가 담깁니다. 나중에 같은 조건으로 다시 실행하거나 결과를 비교할 때 참고할 수 있어요.

## 11. 실습 환경에서 명령을 읽는 방법

가상환경은 프로젝트에 필요한 Python 패키지를 분리합니다. CUDA는 NVIDIA GPU에서 계산하는 경로이며, CPU와 GPU는 사용하는 장치가 다릅니다. [빠른 시작](00_quickstart.md)에서 장치에 맞는 PyTorch와 고정 버전 라이브러리를 준비합니다. 모든 명령은 프로젝트 루트에서 실행합니다.

```bash
source .venv-lab/bin/activate
python scripts/doctor.py
python 01_instruction/pytorch/train.py --dry-run
```

가상환경을 활성화하면 해당 환경의 `python`을 사용할 수 있습니다. Dry-run은 데이터 확인이며 가중치를 바꾸지 않습니다. 작은 PyTorch/HF 텍스트 full·LoRA 실습은 CPU도 가능하지만 실제 학습은 CUDA를 권장합니다. QLoRA·Unsloth·post-training은 별도 GPU 지원 조건이 있습니다.

컨테이너는 CUDA 같은 시스템 환경까지 묶고, 가상환경은 Python 패키지를 분리합니다. DGX Spark 사용자는 [전용 환경 안내](04_dgx_spark.md)의 컨테이너 안에서 실습 환경을 활성화하세요. 이 선택 환경의 설치 절차를 일반 CPU/CUDA 환경에 그대로 따라 하지 마세요.

## 12. 처음 실행하면 무엇을 볼 수 있나요?

[빠른 시작](00_quickstart.md)을 따라 demo 데이터를 준비한 뒤, 아래 명령을 활성화한 실습 환경에서 실행합니다. 마지막 `--smoke-model` 명령은 학습이므로 환경 확인만 할 때는 실행하지 마세요.
이미 `data/demo/instruction`이 준비되어 있다면 첫 데이터 준비 명령은 건너뛰고 기존 파일을 사용하세요.

```bash
python -m finetune_lab.prepare_data --task instruction --source demo --output-root data/demo
python 01_instruction/pytorch/train.py --data-dir data/demo/instruction --dry-run
python 01_instruction/pytorch/train.py --data-dir data/demo/instruction \
  --smoke-model --device cuda --dtype auto --batch-size 2 \
  --gradient-accumulation 2 --max-steps 2 --max-length 64 \
  --output-dir outputs/foundations-smoke
```

이미 데이터나 모델이 저장된 폴더가 있으면 기존 결과를 덮어쓰기보다 새 출력 폴더 이름을 골라 주세요.
Dry run에서는 `train_examples`, `validation_examples`, `test_examples`, `dry_run: true` 같은 정보가 출력됩니다.
Demo instruction 데이터는 24/8/8개 예제로 구성됩니다. GPU를 학습시키지 않고 파일과 분할을 확인하는 단계입니다.
학습 중에는 다음과 같은 형태의 로그를 보게 됩니다. **숫자는 형식을 보여 주는 가상 예시입니다.**

```jsonl
{"step":1,"train_loss":4.8}
{"step":2,"train_loss":4.6}
```

여기서 step 2는 optimizer가 두 번 업데이트됐다는 뜻입니다. 위 설정은 train 24개 중 약 8개 입력을 처리합니다.
실제 loss는 모델·예제·seed에 따라 다르고, 짧은 실행에서 반드시 감소하지도 않습니다.
`--smoke-model`은 랜덤 tiny 모델의 실행·저장 경로 점검입니다. 사전학습 모델의 fine-tuning 품질을 보여 주는 실험이 아닙니다.
그다음 실제 base 모델과 실제 데이터를 사용해 학습 전 평가, 학습, 별도 재로딩, 학습 후 평가를 진행해 보세요.
Train loss가 내려가도 validation 답이 나빠지거나, 정답률이 오르지 않거나, 기존 능력이 떨어질 수 있어요.
“실행 성공”, “저장·재로딩 성공”, “유효한 답 생성”, “성능 개선”을 각각 확인하고 실제 답변도 직접 읽어 보세요.

## 13. 익숙해졌다면 수식도 읽어 볼까요?

이제 [이론 문서](01_theory.md)의 `L(θ) = -평균 log pθ(정답 토큰 | 앞의 토큰)`을 읽어 볼까요?
`θ`는 학습할 가중치 전체, `pθ`는 그 가중치로 계산한 확률, 평균은 loss를 계산하는 정답 위치들의 평균입니다.
이번 수업의 정답 확률 표를 여러 예제와 답변 토큰으로 확장한 식이라고 생각하면 됩니다.
`∇θL`은 여러 가중치의 기울기를 묶은 gradient이고, 단순한 업데이트는 `θ새 = θ현재 - 학습률 × ∇θL`입니다.
AdamW 같은 실제 optimizer는 gradient 기록 등을 사용하므로 이 한 줄보다 더 많은 계산을 합니다.

LoRA의 `W' = W + (α/r)BA`에서는 `W`가 고정된 원래 행렬이고 `A`, `B`가 학습하는 작은 추가 행렬입니다.
앞에서는 숫자 하나를 바꿔 봤지요. 이제는 많은 숫자가 들어 있는 행렬을 바꾸는 학습으로 넓혀 보면 됩니다.
어려운 기호가 나오면 이 페이지의 확률 표, 작은 업데이트, batch 계산 중 어느 부분을 확장한 것인지 먼저 연결해 보세요.
다음 학습은 [커리큘럼](11_curriculum.md)의 첫 PyTorch full 실습에서 시작하고, 마친 뒤 HF LoRA로 넘어가 보세요.

## 14. 스스로 확인해 보세요: 먼저 답하고 해설을 읽어 보세요

1. Token ID가 크면 그 토큰이 더 중요한가요?
2. 정답 확률 0.2와 0.8 중 어느 쪽 loss가 작을까요? Loss 0.7은 정답률 70%인가요?
3. 예제 8개, batch 2, accumulation 2에서 1 epoch는 optimizer step 몇 번인가요?
4. Prompt의 labels가 -100이면 모델이 prompt를 보지 못하나요?
5. EOS와 padding의 ID가 같을 때 모두 loss에서 제외해도 될까요?
6. Train loss가 감소하면 test 점수도 반드시 오를까요?
7. LoRA adapter 파일만 다른 base 모델에 붙이면 같은 결과가 나올까요?
8. Dry run 성공과 랜덤 smoke 모델 성공은 실제 모델의 GPU 학습·성능 개선을 보장할까요?

- 정답 1: 아니에요. ID는 tokenizer의 조각을 구분하는 번호입니다.
- 정답 2: 0.8의 loss가 더 작습니다. Loss는 정답 확률로 계산한 오류값이고 정답률의 백분율이 아닙니다.
- 정답 3: 4개 microbatch를 처리하고 gradient를 두 batch씩 모으므로 optimizer 업데이트는 2번입니다.
- 정답 4: 아니에요. 입력에는 남아 있으며 답을 예측하는 조건입니다. 정답 loss 계산에서만 제외됩니다.
- 정답 5: 안 됩니다. 실제 EOS는 종료 학습에 사용하고 길이 맞춤용 padding 위치만 제외합니다.
- 정답 6: 아니에요. 외운 예제에서 좋아져도 새로운 문제에서 나빠질 수 있으므로 분리해서 평가합니다.
- 정답 7: 아니에요. 동일한 원래 모델과 revision, adapter, tokenizer를 함께 읽어야 재현할 수 있어요.
- 정답 8: 아니에요. 두 점검의 범위는 다르며 실제 base 모델의 학습과 전후 평가가 따로 필요합니다.
